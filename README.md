# call-manager

Internal hospital tool that aggregates funding calls (grants, EU calls, Vinnova programmes, etc.) from multiple sources, ranks them with a local LLM against organization- and group-level research profiles, and surfaces the most relevant calls via a web dashboard and weekly email digest.

## Ranking, walked through

Imagine a new funding call has just arrived from Vinnova: *"Precisionsmedicin: AI-baserad bilddiagnostik"*. We need to decide how relevant it is to a specific research group — say, the hospital's pathology group, whose profile says *"AI-assisted diagnosis of cancer biopsies, with a focus on histopathology image analysis."*

The system goes through six steps. Most of them happen in milliseconds; only one of them (step 3) is slow.

### Step 1 — The call gets read in and "summarized as numbers"

When the call arrives from the source, the system does two things to its text:

- **Stores the text** (title + summary + full body) verbatim in the database.
- **Computes an "embedding"** — a list of 1,024 numbers that represents the *meaning* of the text, generated by a model called BGE-M3.

You can think of an embedding as a fingerprint of meaning: two texts about the same topic produce similar fingerprints, two texts about different topics produce different ones. The actual numbers are meaningless to humans, but a computer can compare them very fast.

The same fingerprint was computed for the profile's description when it was written.

> **Why this exists:** so we can do a quick "are these two things even talking about the same topic?" check later, without spending GPU time on the slow LLM.

### Step 2 — Four fast checks (the "gates")

Before anything expensive happens, the system runs four quick checks. Each one returns one of three answers: **pass**, **fail**, or **unknown** ("I don't have enough info to say").

| Check | What it asks |
|---|---|
| **Timeline** | Is the deadline at least 14 days away? |
| **Budget** | Does the call's budget range overlap with what the profile says it can absorb (and in the same currency)? |
| **TRL** | Are the technology-readiness levels compatible? (Hospital usually wants TRL 3–7; an industrial call might want TRL 7–9.) |
| **Topic similarity** | Are the two fingerprints from step 1 similar enough? (Specifically, is the cosine between them ≥ 0.30?) |

If **any** check returns **fail**, the system stops here and gives the call a final score of **0**, with the failing check name as the reason. No LLM is ever called for this call×profile pair.

For our cancer-biomarker example: timeline passes (deadline is months away), budget is "unknown" (the profile doesn't have a budget filter), TRL is "unknown" (neither side specified), and topic similarity is high (~0.62). All gates pass — proceed to step 3.

For an irrelevant call (e.g., manufacturing automation): topic similarity would be ~0.18, the topic gate fails, score = 0, no LLM call. **This is the embedding pre-filter — it's the cheapest way to throw out clearly off-topic calls.**

> **Why "unknown" exists:** funding bodies don't always publish a budget or TRL range. Treating "missing data" as "fail" would reject perfectly good calls. So missing data means "let the LLM decide" rather than "no".
>
> **Escape hatch:** if the profile has special "force-include" keywords (e.g., the group says *"always show me anything mentioning ferroptosis"*), the topic and timeline gates are bypassed. Budget and TRL are not — those are hard constraints regardless of topic.

### Step 3 — The expensive check: ask the LLM for a rubric

Only if all gates passed (or were "unknown") do we spend GPU time. The system sends the LLM (Gemma 4 E4B running on the local GPU server) a structured prompt asking for three judgments — see the next section *What's a "rubric"?* for what those judgments are and why.

For our cancer-biomarker example, the LLM returns 5/5 topic fit, eligibility = pass, exclusions = pass.

### Step 4 — The system verifies the LLM's quotes

LLMs sometimes invent quotes that look plausible but aren't actually in the source ("hallucination"). The system checks each quoted snippet against the actual call text (whitespace-tolerant, case-insensitive). If a quote doesn't actually appear in the call body, **the quote is silently nulled** (so the operator doesn't see fake evidence) — but the score itself is **not** demoted, because a hallucinated quote doesn't necessarily mean the judgment was wrong.

> **Why we don't demote on quote failure:** the LLM might judge a call correctly but paraphrase the supporting quote rather than copy it verbatim. Penalizing the score for that would over-correct. The right thing is to just hide the bad quote and trust the judgment.

### Step 5 — Combine the rubric into a 0–100 score

A simple deterministic table turns the rubric into a single score:

| Situation | Final score |
|---|---|
| Any gate failed (step 2) | 0 |
| LLM says eligibility = fail | 0 |
| LLM says exclusions = fail | At most 10 (force the call near the bottom regardless of topic fit) |
| LLM says eligibility = unclear | At most 50 (cap at borderline — operator should review) |
| Otherwise (clean path) | topic fit × 20 (so 5/5 = 100, 4/5 = 80, 3/5 = 60, etc.) |

For our cancer-biomarker example: topic fit 5 × 20 = **100**.

> **Why a deterministic table:** the LLM does the *judging* (which is hard); the *combining* is a fixed formula that humans can verify and tune. If you change "what counts as a top match", you edit this table — you don't retrain the LLM.

### Step 6 — What the operator and researchers see

The score plus everything that produced it is written to the database:

- The **0–100 score** and the **reason** (which gate failed, or `null` for the clean path)
- A one-line **summary** for the calls-index page
- A row per criterion with its rating, rationale, and verified quote, displayed on the call-detail page
- The **embedding similarity number** (the cosine from step 2) — useful when tuning the topic-similarity threshold
- The **prompt version** (currently `v3.0`) — so we can tell which version of the rubric produced this score

A researcher visiting `/calls?profile=<their-group>` sees the calls sorted by score (high to low). Each Monday at 07:00, the highest-scoring calls of the past week are emailed in a digest, with the borderline ones (45–60) in a separate section.

### When things go wrong (graceful degradation)

| Failure | Effect |
|---|---|
| Local LLM server (Ollama) is down at rank time | Embedding can't be computed → topic gate becomes "unknown" → fall through to LLM step → if LLM is also down, the ranking job is marked failed and retried later. |
| The call's body text couldn't be scraped (e.g., HTML page returned 404) | `full_text` stays empty → LLM sees only title + abstract → ranking still works, just with less context. |
| Source's API changed and we get garbage back | The adapter raises an alert (after 3 consecutive failures, an admin email goes out). |
| A profile has no description | Profile embedding is null → topic gate becomes "unknown" → LLM runs as fallback. |

The system is designed so that **every failure mode is "LLM runs as fallback"** rather than "no ranking at all". The cheap optimizations (embedding pre-filter, gates) are improvements, not requirements — if they don't work, the LLM still runs and produces a score.

## What's a "rubric"?

A **rubric** is a structured scoring framework with multiple dimensions — instead of asking for one summary judgment, you break the question into separate sub-questions, each with its own scale and its own justification.

It's the same idea a teacher uses to grade an essay: rather than just slapping "B+" on it, the teacher fills in:

| Dimension | Scale | This essay |
|---|---|---|
| Thesis | 0–5 | 4 |
| Evidence | 0–5 | 3 |
| Structure | pass / unclear / fail | pass |
| Mechanics | pass / fail | pass |

Then a fixed formula turns those into the final letter grade. The benefit: when a student asks "why a B+?", the teacher can point at "thesis was strong but evidence was thin" — not just "vibes."

The call-manager rubric works the same way. Instead of asking the LLM *"score this call 0–100"*, it asks for three separate judgments, each with its own scale and its own justification.

### Why a rubric instead of one big number

Three concrete reasons:

1. **Different dimensions need different scales.** Topic relevance is a continuum (a call can be "kind of about your topic"). But eligibility is more like a gate: either you can apply or you can't. And exclusions are binary deal-breakers. Forcing all three through the same 0–100 channel loses information.
2. **You can spot-check the LLM's reasoning.** When a score comes back as 80, you can look at the call-detail page and see *"the LLM said topic fit is 4/5 because the call's about cancer biomarkers and your profile is too — but eligibility is unclear because they didn't specify whether non-EU institutions can apply."* That's debuggable. A bare "80" isn't.
3. **You can change the combining formula without retraining the LLM.** The LLM judges each dimension independently. The Python code combines them according to a small table (the one in step 5 above). If you decide *"actually, an unclear-eligibility shouldn't cap the score at 50, only 60"*, you change one line in the aggregator. The LLM's behavior doesn't change at all.

### The three dimensions in this system

| Dimension | Scale | What it asks |
|---|---|---|
| **topic_fit** | 0–5 (integer) | "How well does this call match the profile's stated research focus?" |
| **eligibility** | pass / unclear / fail | "Could a clinical research group at an EU institution actually apply for this?" |
| **exclusions** | pass / fail | "Does this call hit any of the profile's hard exclusions (animal-only research, drug discovery, etc.)?" |

These three are deliberately **orthogonal** — they ask different questions:

- A call could be perfectly on-topic but ineligible (e.g., requires an SME applicant; the hospital isn't one).
- A call could be eligible but irrelevant (e.g., the hospital qualifies but the topic is industrial automation).
- A call could be on-topic AND eligible but hit a hard exclusion (e.g., requires animal models, which the profile rules out).

All three have to be okay for a high final score. That's why the aggregation formula has separate short-circuits: any FAIL on eligibility zeroes the score; any FAIL on exclusions caps it at 10; an "unclear" eligibility caps it at 50 (borderline — needs human review).

### What the LLM returns: the structured shape

The LLM is told to return JSON in this exact shape:

```json
{
  "topic_fit": {
    "rating": 4,
    "rationale": "Direct match on AI image diagnosis…",
    "quoted_evidence": "AI-based image diagnostics for cancer screening"
  },
  "eligibility": {
    "rating": "pass",
    "rationale": "Clinical research groups at EU institutions are eligible.",
    "quoted_evidence": "Eligible: clinical research groups at EU/EEA institutions"
  },
  "exclusions": {
    "rating": "pass",
    "rationale": "No animal-model or drug-discovery requirement.",
    "quoted_evidence": null
  }
}
```

Three structural choices worth noticing:

- **Each judgment is its own object**, not a flat list of sub-scores. This forces the LLM to commit to a specific value for `rating`, separately from the explanation. (Asking for a flat *"topic: 4 because reasons"* tends to produce drifty, non-structured output.)
- **`rationale`** is a short prose explanation, displayed on the call-detail page so a human can see *why*.
- **`quoted_evidence`** is a verbatim snippet from the call body — the accountability lever (see step 4 above).

### Where the rubric lives in the code

Two files:

| What | Where |
|---|---|
| **The rubric prompt** (the questions, the scales, the JSON shape the LLM must return) | [`src/call_manager/ranking/prompt.py`](src/call_manager/ranking/prompt.py) — the `_SYSTEM_TEMPLATE` and `_USER_TEMPLATE` strings |
| **The combining formula** (how the rubric becomes a 0–100 score) | [`src/call_manager/ranking/aggregate.py`](src/call_manager/ranking/aggregate.py) — the `aggregate()` function with its short-circuit chain |

Tuning the system is split between the two:

- *"What does 'topic fit' actually mean?"* → edit the prompt template.
- *"Should an unclear eligibility cap at 50 or 60?"* → edit the aggregator.
- *"Should we add a fourth dimension?"* → edit both, plus bump `PROMPT_VERSION`.

### Why versioning the rubric matters

Every CallRanking row stores which version of the rubric prompt produced it (`prompt_version` column, currently `"v3.0"`). When you change the rubric in any meaningful way — add a dimension, change a scale, reword a question — you bump the version. This lets you:

- **Compare scores across versions:** *"did changing the prompt actually improve quality, measured against the curated golden-set?"*
- **Identify which scores are stale:** *"after the v3.0 bump, all v2.0 rows should be re-ranked."*
- **Audit historical data:** *"this score from 6 months ago was produced under the old eligibility rubric."*

We did this in Plan F: bumping from `v2.0` → `v3.0` because the rubric started seeing `summary + full_text` instead of just `summary`. Same questions, same scales — but the LLM's input changed materially, which counts as a rubric change for audit purposes.

### One-line summary

A rubric is **the LLM's grading sheet** — a fixed set of dimensions, a fixed set of allowed answers, a fixed format for explaining each answer. The LLM's job is to fill in the grading sheet honestly; the system's job is to combine the filled-in sheet into a single number you can sort by.

## What it does

- **Ingests** funding calls from external sources on a schedule (Vinnova two-stage API, EU Funding & Tenders Portal). Adapters are pluggable.
- **Ranks** each `(call × profile)` pair through a single criterion-rubric pipeline: rule-based gates (timeline / budget / TRL / embedding cosine) → LLM rubric call (topic-fit, eligibility, exclusions) → deterministic aggregation into a 0–100 `aggregate_score`.
- **Surfaces** results via a server-rendered FastAPI + HTMX dashboard with per-profile ranking, per-criterion explanation, and admin observability (queue depth, embedding coverage, last-run Kendall's τ).
- **Emails** a weekly digest per profile (top + borderline bands).

The ranking module is deliberately model-agnostic — swapping Gemma 4 for a hosted API or a larger local model is a config change.

## How it works

### Profiles — what you're matching against

A **profile** describes either a research **organization** (e.g. the hospital) or a **group** (e.g. a single PI's lab). It carries:

- A free-text **description** (a few sentences of research focus, used as system-prompt context AND as the input text to the embedding model)
- A **structured rubric** stored as JSONB: `areas` (named research areas), `must_include` (force-include keywords for borderline calls), `hard_exclusions` (deal-breakers — drug discovery, animal models, etc. — that the LLM judges as `exclusions = fail`, after which the aggregator caps the final score at 10), plus optional `budget_min` / `budget_max` / `trl_min` / `trl_max`
- A `budget_currency` (3-letter ISO code) used for budget-gate currency matching
- An `embedding` (BGE-M3, 1024-dim) refreshed by the embeddings backfill tick

### Ingestion → enqueue → drain → rank

1. **Source adapters** (Vinnova, EU Funding & Tenders Portal) run on cron jobs at 03:00 / 03:15 Europe/Stockholm. Each adapter normalizes the source's API into a common `Call` row with `title`, `summary`, `full_text`, `deadline`, `budget_min` / `max` / `currency`, `keywords`, plus a `structured` JSONB blob for source-specific extras (TRL ranges, programme codes, etc.). Vinnova uses a two-stage API: list endpoint → detail fetch per call.
2. **Embedding** happens inside ingestion: each new or updated `Call` is embedded immediately so the embedding pre-gate has data on the next ranking tick. A daily 03:30 backfill tick (`embeddings:refresh-missing`) catches anything that failed during ingest or was added without embedding (e.g. via tests/manual SQL).
3. New calls trigger a **per-active-profile fan-out**: for every active `Profile`, a `RankingJob` row is enqueued.
4. The **`rank:drain` worker tick** runs every `RANKING_TICK_SECONDS` (default 60s). It claims a small batch of `PENDING` jobs (`SELECT … FOR UPDATE SKIP LOCKED`), dispatches each through `rank_pair`, writes the result to `call_rankings` (PK: `call_id, profile_id`), and marks the job `DONE` or `FAILED`.

### Ranking pipeline — one path, four gates + an LLM rubric

`rank_pair` ([src/call_manager/ranking/rank_pair.py](src/call_manager/ranking/rank_pair.py)) decomposes the relevance question into **deterministic gates** + a **structured LLM rubric** + a **deterministic aggregation**:

**1. Rule-based gates** ([src/call_manager/ranking/criteria.py](src/call_manager/ranking/criteria.py)) — evaluated in pure Python before the LLM is touched:

| Gate | PASS condition | UNKNOWN condition | FAIL condition |
|---|---|---|---|
| **timeline** | `deadline >= now + 14 days` | `deadline is None` | expired or `< 14 days` away |
| **budget** | profile and call budget ranges overlap AND currencies match | any field missing, or currencies present but mismatch | ranges don't overlap |
| **TRL** | TRL ranges overlap | any TRL field missing | ranges don't overlap |
| **embedding** | cosine(profile, call) ≥ `EMBEDDING_PREGATE_THRESHOLD` (default 0.30) | either embedding missing OR embedded under different models | cosine below threshold |

A FAIL on any gate **short-circuits the LLM call** — the result is `aggregate_score = 0` with the gate name as `aggregate_reason`. UNKNOWN is *not* FAIL: source adapters frequently don't populate budget or TRL, and treating null as fail would reject valid calls.

The **`must_include` profile keyword override** is a partial escape hatch: if the call's title / summary / keywords match a must-include term, both the timeline and embedding FAILs are bypassed (those are topic gates and must-include is the user's "I want to see this regardless" signal). Budget and TRL FAILs still hard-zero the score even with override.

**2. LLM rubric call** ([src/call_manager/ranking/prompt.py](src/call_manager/ranking/prompt.py)) — only fires if all gates pass (or were UNKNOWN, or were bypassed by must-include). The system prompt asks the model to act as a research-funding analyst evaluating a call for the given profile. It returns a JSON object with three sub-rubrics:

```json
{
  "topic_fit":   {"rating": 0..5,         "rationale": "...", "quoted_evidence": "..."},
  "eligibility": {"rating": "pass|unclear|fail", "rationale": "...", "quoted_evidence": "..."},
  "exclusions":  {"rating": "pass|fail",  "rationale": "...", "quoted_evidence": "..."}
}
```

The user-prompt template carries `title`, `programme`, `deadline`, and `budget` in dedicated fields; the call's body — `summary + full_text` concatenated with `\n\n`, truncated to `CALL_TEXT_LIMIT` (16 000 chars, set in `prompt.py`) — goes in the `text` field. The model is instructed to set `quoted_evidence` to a verbatim span from the call (truncated to 200 chars) for any non-default judgment. The Ollama call uses `response_format={"type": "json_object"}` to enforce object shape.

**3. Quoted-evidence verification** — for each non-null `quoted_evidence`, the parser checks it appears as a (whitespace-tolerant) case-insensitive substring of `title + summary + full_text` (FULL full-text — no truncation, so quotes from past the 16 KB prompt cap still verify). Verification failures null out the field; they never demote the score.

**4. Score aggregation** ([src/call_manager/ranking/aggregate.py](src/call_manager/ranking/aggregate.py)) — combines gates + LLM into a final 0–100 score:

| Condition | Score |
|---|---|
| Any gate FAIL (timeline / budget / TRL / embedding) | 0 |
| `eligibility == "fail"` | 0 |
| `exclusions == "fail"` | `min(10, topic_argmax × 2)` |
| `eligibility == "unclear"` | `min(50, topic_argmax × 20)` (capped at borderline) |
| Clean path | `topic_argmax × 20` |

The score is written to `call_rankings.aggregate_score` along with: rationale (a one-line per-criterion summary plus the per-criterion rationales as separate `call_ranking_criteria` rows), prompt version, model name, `embed_similarity` for downstream analysis, and the raw JSON envelope for audit.

### Read paths — what the user sees

- **Calls index** (`/calls?profile=<id>`): Postgres query `JOIN call_rankings ON call_id … WHERE profile_id = ?`, ordered by `aggregate_score DESC`.
- **Call detail** (`/calls/<id>?profile=<id>`): the full ranking, including the per-criterion table loaded from `call_ranking_criteria` — topic rating with rationale + verified quoted evidence, eligibility verdict, exclusions verdict, plus any gate FAIL reason.
- **Weekly digest**: per-profile email, sent Monday 07:00 Europe/Stockholm. Buckets: **must-include** (matched a must-include keyword, any score), **top** (`aggregate_score ≥ 60`), **borderline** (`45 ≤ aggregate_score < 60`). Recently-sent and user-dismissed calls are excluded (prior digests bounded to the last 26 weeks). Rendered HTML + plain-text via Jinja templates; sent through the configured SMTP/Resend client (or the `NoOpEmailClient` in dev).

### Operational tooling

- **`/admin`** shows source health (per-source last-fetched + call count), ranking-queue depth by status, **embedding coverage** (calls and profiles embedded vs stale, against the currently-configured embedding model — blank-description profiles are excluded since they can't be embedded by design), digest panel (last sent, runs this week, disabled users from bounce-handling), and the most recent golden-set Kendall's τ.
- **`/admin/rerank`** enqueues jobs for every active profile × every Call from the last 90 days. Idempotent (partial unique index dedups in-flight jobs).
- **Weekly golden-set evaluator** at Mon 06:00: reads `tests/fixtures/golden_set.json` (curated `(call_id, profile_id, expected_score)` triples), queries `call_rankings`, computes Kendall's τ-b inline (pure stdlib, ties-aware), persists the result to `data/golden_set_last.json` for `/admin` to read.
- **Embeddings backfill CLI** ([src/call_manager/embeddings/cli.py](src/call_manager/embeddings/cli.py)) — `python -m call_manager.embeddings.cli backfill` walks every call + profile with NULL or model-mismatched embedding, calls Ollama in batches, exits 0 on full success / 1 if any row failed. Pass `--force` to re-embed every row regardless (used in content-rollout deploys; see "Deploy procedure" below). Pagination via id-cursor in force mode so a transient batch of failed rows doesn't stop the run. **In `--force` mode, an Ollama failure on a row clears both `embedding` and `embedding_model` to NULL** — the daily refresh tick will then re-select the row via its `IS NULL` filter and retry. Trade-off: that row degrades to LLM-only ranking until the next successful embed, which is safer than ranking against a known-stale vector.
- **Forced-ingest CLI** ([src/call_manager/ingestion/cli.py](src/call_manager/ingestion/cli.py)) — `python -m call_manager.ingestion.cli run --source <slug>` triggers a single ingest tick from the command line (without waiting for the 03:00 / 03:15 cron). `… list-sources` prints registered slugs from `sources/registry.SOURCES`. Exit 1 on adapter or DB failure so deploy scripts can chain on `&&`.

- **Tests** — `pytest` + `testcontainers[postgres]` (uses the `pgvector/pgvector:pg16` image), `httpx.MockTransport` for LLM stubbing

## Deploy procedure

The supported deploy sequence depends on what the new code touches:

### Routine deploy (schema or app changes only)

```bash
alembic upgrade head
python -m call_manager.embeddings.cli backfill
systemctl restart call-manager    # only after the CLI exits 0
```

### Content-rollout deploy (changes to ingestion content, prompt, or embedding model)

When a deploy alters what the LLM/embedding sees — e.g., new adapter fields populated into `Call.full_text`, a `PROMPT_VERSION` bump, or an `EMBEDDING_MODEL` swap — existing rows are **stale** and must be refreshed. The full sequence:

```bash
# 1. Schema (no-op when there are no migrations).
alembic upgrade head

# 2. Reset the per-source incremental-fetch cursor so the next ingest re-fetches
#    the historical window. NULL is correct: the orchestrator falls back to
#    epoch when last_fetched_at IS NULL, guaranteeing every historical row
#    is re-fetched regardless of when it first appeared.
psql -c "UPDATE sources SET last_fetched_at = NULL WHERE slug IN ('vinnova', 'eu_portal')"

# 3. Force-ingest both sources to repopulate Call rows under the new adapter logic.
#    Both CLIs exit 1 on adapter or DB failure, so chaining with && is safe.
python -m call_manager.ingestion.cli run --source vinnova && \
python -m call_manager.ingestion.cli run --source eu_portal

# 4. Re-embed every call + profile under the now-richer text or new model.
#    --force drops the NULL/mismatched filter so already-embedded rows are
#    re-embedded too. Exits 0 on full success / 1 if any row failed.
python -m call_manager.embeddings.cli backfill --force

# 5. Re-rank existing CallRanking rows under the new prompt. Hit /admin/rerank
#    from the admin UI after step 4 completes; it enqueues every (active
#    profile × call from the last 90 days) and the drain tick processes them
#    over the next ~hour at typical scale.

# 6. Restart the app.
systemctl restart call-manager
```

**Why this order:**

1. **`alembic upgrade head` runs first** so the schema matches the new code. Migrations are intentionally schema-only — they never call out to Ollama. Embedding backfills used to be tempted into Alembic data migrations, but a migration that depends on an external HTTP service makes deploys fragile (Ollama down → schema deploy stuck mid-migration). The CLI is the explicit, separate, retryable step.
2. **Cursor reset (`UPDATE sources … = NULL`)** undoes the modified-since optimization for one ingest cycle. Without it, the next ingest only fetches programmes modified after the previous run — historical rows would silently retain their old `summary`/`full_text` values forever.
3. **`ingestion.cli run --source X`** drives a one-shot ingest immediately rather than waiting for the next 03:00/03:15 cron. With cursors at NULL, this re-fetches every historical row and runs the new adapter logic against it.
4. **`embeddings.cli backfill --force`** re-embeds everything — both NULL/mismatched rows AND already-embedded rows whose source text has changed. The default (no `--force`) only handles NULL/mismatched.
5. **`/admin/rerank`** re-runs the ranking pipeline against the fresh content under the new `prompt_version`. Without this step, existing CallRanking rows still reflect the OLD prompt's view.
6. **Restart the app last**, after the CLIs have reported success. The new code is now backed by an up-to-date schema, fully-populated content, fresh embeddings, and re-ranked outputs.

The `/admin` page surfaces an embedding-coverage badge — a quick post-deploy sanity check that the backfill succeeded.

## Renamed from `call-monitor` (B2 cutover)

The project was renamed from `call-monitor` to `call-manager` in 2026-05.
For production deployments crossing the rename boundary:

1. Stop the running app process (so no sessions hold the old database open).
2. Run the cutover script as a Postgres superuser:
   ```bash
   PGUSER=postgres PGHOST=... bash scripts/cutover_rename_database.sh
   ```
3. Update `DATABASE_URL` in the deployment's env to point at `call_manager`
   (user, password, and database name all `call_manager`; the dev default
   matches `.env.example`). **If your deployment was NOT using the dev-default
   password**, rotate it now — the cutover script restores the dev default
   (`'call_manager'`); change it via `psql -c "ALTER ROLE call_manager WITH
   PASSWORD '...'"` before bringing the app up.
4. Start the new app process with the updated env.
5. (Optional cleanup) Prune the orphaned Docker volume from the old name:
   ```bash
   docker volume rm <stack-name>_call_monitor_pgdata
   ```
   The new `call_manager_pgdata` volume now holds the live data; the old
   one is unused and consumes disk.

The cutover script is idempotent: a second invocation after success is a no-op.

**Side effect of the rename:** Task 2's commit also changed the session-cookie
salt from `"call-monitor-session"` to `"call-manager-session"`, which invalidates
existing session cookies. All active users will be forced to re-authenticate.
For a pre-production deployment this is no concern; for a live deployment with
active sessions, plan a brief downtime announcement.
