# Call Manager — Ranking v2.1: Score Quality, Outcome-Based Escalation, and the Eval Loop

**Date:** 2026-06-11
**Status:** Approved design (brainstorm complete; revised same day for Codex
review findings R1–R8 — tagged inline)
**Companion specs:**
- [2026-04-17-ranking-v2-criterion-design.md](./2026-04-17-ranking-v2-criterion-design.md) — criterion rubric, gates, aggregation
- [2026-04-18-ranking-v2-d-embedding-prefilter-design.md](./2026-04-18-ranking-v2-d-embedding-prefilter-design.md) — embedding pre-gate
- [2026-06-05-profile-redesign-design.md](./2026-06-05-profile-redesign-design.md) — structured profile namespaces

**Relationship to existing work:** v2 ranking (gates + LLM rubric + cosine escalation router) is implemented and live. This spec is an additive evolution — no scheme change, no rewrite. It implements the G-Eval logprob weighting the v2 spec planned but never shipped, replaces the cosine-based Sonnet router with outcome-based escalation, and stands up the eval loop that v2 left empty.

## 1. Problem statement

Five defects, in priority order:

1. **The 0–100 score is a 6-point scale in disguise.** `aggregate()` computes
   `topic_argmax × 20`, so the only achievable scores are
   {0, 2, 4, 6, 8, 10, 20, 40, 50, 60, 80, 100}. Two user-visible consequences:
   - The digest "borderline" band [45, 60) can only ever contain the value 50,
     which only arises from the eligibility-unclear cap. The bucket is silently
     "topic ≥ 3 but eligibility unclear", not "scored borderline".
   - Within-bucket ordering (`ORDER BY aggregate_score DESC`) is mostly ties
     broken by `profile_id`. Digest top-5 membership turns on one Likert notch
     from a single sample of a Q4-quantized 4B model.

   The v2 spec planned G-Eval logprob-weighted expected value to fix this;
   it was never implemented (`LLMResult.topic_argmax` is even named in
   anticipation). **Verified 2026-06-11:** Ollama 0.21.0 returns `logprobs` +
   `top_logprobs` on `/v1/chat/completions` for `gemma4:e4b-it-q4_K_M`,
   including when `response_format: {"type": "json_object"}` is set.

2. **The golden set is empty.** `tests/fixtures/golden_set.json` contains zero
   triples. The Kendall-tau harness (`ranking/eval.py`) runs against nothing;
   every tuning question (thresholds, prompt changes, Q4-vs-Q8, Sonnet ROI) is
   currently unanswerable. The fixture also lives in the repo, so the running
   app has no write path for curation.

3. **Sonnet escalation routes on the wrong variable.** The cosine ≥ 0.50
   router sends Sonnet the pairs Gemma is *most likely to get right* on topic,
   while eligibility — funder legalese, the genuine weakness of a 4B model —
   is decided locally for everything below the bar. The cutoff is also
   embedding-model-dependent: under dev's mxbai-embed-large (the bge-m3 NaN
   workaround) cosine distributions are compressed upward and 0.50 fires far
   too often.

4. **Cosine thresholds are silently coupled to bge-m3.** The 0.20 / 0.30
   defaults came from BGE-M3's similarity distribution. Nothing warns when
   `EMBEDDING_MODEL` is something else.

5. **Org-profile embeddings miss topical signal.** `build_profile_text()`
   embeds description + areas only. `org.capabilities` and
   `org.patient_populations` (added by the profile redesign) never reach the
   vector, so the pre-gate can cosine-miss a call squarely aimed at a group's
   patient population.

## 2. Decisions log (from brainstorm, 2026-06-11)

| Decision | Choice |
|---|---|
| Scope | All six items in one spec, phased rollout |
| Golden-set storage | New `golden_set_triples` DB table; JSON fixture survives for unit tests only |
| Escalation architecture | **Outcome-based**: Gemma ranks every pair first; local aggregate ≥ threshold re-runs on Sonnet, whose result wins. Cosine router removed. Extended per Codex R3 with the eligibility-fail + topic ≥ 3 trigger (§3.3). |
| Remote score granularity | Sonnet stays argmax (Anthropic API exposes no logprobs); cosine tie-break orders within remote ties |
| "Borderline" bucket rename | Dropped — EV scoring repopulates [45, 60) with real scores, making the existing label honest |

## 3. Design

### 3.1 Logprob expected-value topic scoring (G-Eval)

**Request change.** `OllamaClient.chat()` gains pass-through support for
`logprobs: true, top_logprobs: 10`. Only the local rubric call sets them.

**Extraction.** New pure function in `ranking/prompt.py` (or a sibling
`ranking/ev.py`):

```python
def extract_topic_expected(envelope: dict, parsed_rating: int) -> float | None:
    """Expected value of the topic_fit rating from token logprobs.

    Deterministic offset binding (Codex R7 — a candidate-scan heuristic
    can misbind to rationale prose like "4/5", and JSON key order is not
    guaranteed):

    1. Reconstruct cumulative character offsets for the token stream by
       UTF-8-decoding each logprobs.content[i].bytes entry (verified
       present in the Ollama 0.21.0 envelope).
    2. Locate the value span of topic_fit.rating in the raw content with
       a small string-literal-aware scanner (~30 lines: tracks JSON
       string boundaries + escapes, finds the "topic_fit" object, then
       its "rating" key, then the integer literal that follows). This
       cannot false-match '"rating":' text inside a rationale string.
    3. Select the token whose span covers that integer literal. Sanity
       check: the token text must equal str(parsed_rating).
    4. Collect exp(logprob) over digit tokens "0".."5" in that token's
       top_logprobs, renormalize over the digits found, return Σ d·p(d).

    Returns None (caller falls back to argmax) when:
      - the envelope has no logprobs block (older Ollama, remote client),
      - the scanner cannot locate the rating literal, no token covers it,
        or the covering token fails the sanity check (multi-char token),
      - fewer than 2 distinct digit tokens appear in its top_logprobs
        (degenerate distribution → EV == argmax anyway).
    """
```

**Aggregation change.** `LLMResult` gains `topic_expected: float | None`.
`aggregate()` uses `topic = topic_expected if topic_expected is not None else
topic_argmax` everywhere it currently uses `topic_argmax`:

- clean path: `base = round(topic * 20)` → any int 0–100
- eligibility unclear: `min(base, 50)` — unchanged shape
- exclusions fail: `min(10, round(topic * 2))` — unchanged shape

**Persistence.**
- New nullable column `call_rankings.topic_fit_expected` (double precision).
  NULL ⇒ argmax fallback was used (or pre-v5.0 row). The per-criterion argmax
  rating rows are unchanged.
- **`raw_response` must be stripped of the `logprobs` block before persisting.**
  At `top_logprobs: 10` the block adds tens of KB per row of JSONB. Keep only
  the rating-token's `top_logprobs` slice under a new envelope key
  `_topic_rating_logprobs` for debugging; delete the rest.

**Version bump.** `PROMPT_VERSION` `"v4.1"` → `"v5.0"`. The prompt text is
unchanged but score semantics change regimes, which is exactly what the
constant marks. No forced backfill: old rows stay attributed to v4.1; the
admin rerank path re-scores on demand.

**Remote path.** Anthropic exposes no logprobs; Sonnet results keep
argmax × 20 (quantized) and `topic_fit_expected` NULL. Ordering within remote
ties comes from the cosine tie-break (§3.2). Not worth forking the response
schema to ask Sonnet for float ratings.

**Validation gate before the version flip (P3 acceptance):** a
**non-persisting** validation command (Codex R2 — the admin rerank path is a
90-day bulk backfill that overwrites production `call_rankings` rows, and a
pre-flip branch would label EV scores v4.1; neither is acceptable for a
validation run):

```
uv run python -m call_manager.ranking.validate_ev --sample 50
```

samples ~50 existing LLM-scored pairs (stratified across the score range),
re-runs the local rubric call with logprobs **in memory — zero DB writes**,
and writes a timestamped JSON report to
`$CALL_MANAGER_DATA_DIR/ev_validation_<ISO-timestamp>.json` (per-pair table
plus the three acceptance metrics). EV must (a) populate for ≥ 80 % of
sampled pairs, (b) produce ≥ 5 distinct score values in [40, 100], (c) keep
|EV − argmax| ≤ 1.0 rating points for ≥ 95 % of pairs. Grammar-constrained
decoding can sharpen distributions (probe on 2026-06-11 showed a
near-degenerate top_logprobs on a trivial input); if EV degenerates to
argmax on real data, ship the column anyway and fall back to the
`sample_count` self-consistency route (see Follow-ups) before reconsidering.

### 3.2 Cosine tie-break in ordering

Everywhere results order by `aggregate_score DESC`, the key becomes
`(aggregate_score DESC, embed_similarity DESC NULLS LAST)`:

- `digest/assemble.py`: the top-candidates and borderline-candidates queries;
  the within-bucket Python sort (`key=(score, embed_similarity)`); the
  primary-profile pick gains a cosine element between score and profile_id —
  `(bucket_priority, -score, -cosine, profile_id)` with NULL cosine treated
  as -1.0 so missing vectors lose ties to any real cosine.
- `web/routes/calls.py`: the dashboard with-score list ordering (~line 107)
  **and** the best-fit-profile lookup on the call detail page (~line 252)
  (Codex R4 — both sites order by `aggregate_score DESC NULLS LAST` today;
  both gain the cosine element).

**Stale-cosine preservation removed** (Codex R4). The worker currently
preserves a previously-recorded `embed_similarity` when the current run
produced None (worker.py ~140–153) — a diagnostic courtesy from when the
column was display-only. Once cosine participates in ordering, a preserved
value from a swapped embedding model is exactly the meaningless-cosine case
`_safe_cosine`'s mismatch guard exists to null: it would win ties it has no
claim to. The worker now writes `result.embed_similarity` verbatim (NULL when
this run had none → sorts last). Diagnostics survive via the
`embedding_model_mismatch` WARNING log and the admin coverage panel, and the
next rerank after an embedding backfill restores a real value.

Display changes: none. Cosine never alters a score, only breaks ties.
The existing `ix_call_rankings_profile_score` index still serves the
profile + score prefix; the residual cosine sort runs over the small
per-profile tail — no index change.

### 3.3 Outcome-based Sonnet escalation (replaces the cosine router)

**`rank_pair` flow change** (`ranking/rank_pair.py`):

1. Gates evaluate exactly as today (including the embedding pre-gate and
   must_include bypasses). Gate FAILs short-circuit — never escalate.
2. Local LLM (Gemma) runs for every gate-passing pair, `enable_analysis=False`.
3. Compute the local aggregate. If `remote_client is not None` (API key
   configured, daily cap not exhausted — see worker below) **and either**:
   - local `agg.score >= escalation_min_score` (new setting, default 45 —
     mirrors `DIGEST_BORDERLINE_LOWER`), **or**
   - local eligibility == `fail` with topic_fit argmax ≥ 3 (Codex R3:
     an eligibility fail aggregates to 0, so the score branch alone can
     never re-examine exactly the failure mode this spec names as the 4B
     model's weakness — false-negative legalese judgments on high-topic
     calls. The unclear case already escalates via the 50-cap ≥ 45;
     this adds the fail case. Low topic stays dead: off-topic anyway.)

   then re-run the pair on the remote client with `enable_analysis=True`,
   re-parse with the same quote-verification text, re-aggregate with the same
   gates and `must_include_override`. **The remote result replaces the local
   one unconditionally on success** — even when Sonnet demotes the pair below
   the threshold (that disagreement is mining signal #3, §3.4).
4. Result fields: `model` = remote model, `summary`/`applicant_notes` from
   Sonnet, plus new `escalated=True`, `escalated_from_score=<local score>`.
   Escalated rows persist `topic_fit_expected` NULL — the stored score is
   Sonnet's argmax, and storing the discarded local EV beside it would
   mislead; the local signal survives as `escalated_from_score`.

must_include pairs get no special treatment: they escalate iff their local
score independently clears the threshold (the must_include digest bucket
already surfaces them regardless of score).

The `remote_cosine_threshold` parameter and the cosine router block are
deleted. `_safe_cosine` and `embed_similarity` persistence are unchanged (the
pre-gate and tie-break still need them).

**Failure semantics (asymmetric, deliberate):**
- Local `ParseError`/`LLMError`: unchanged — raises; worker retries /
  dead-letters. There is no usable result.
- Remote `LLMError` **or** remote `ParseError`: caught inside `rank_pair`;
  keep the local result (`escalated=False`), log
  `ranking.escalation_failed` with the error class. The job succeeds — a
  valid local score exists. A Sonnet outage degrades quality, not coverage;
  admin rerank re-escalates after recovery. The attempt is still recorded
  in the ledger below — a paid remote call is a paid remote call.

**Daily cap counts attempts, not rows** (Codex R1). `call_rankings` is
merge-upserted in place, so counting `escalated` rows undercounts repeated
reranks of the same pair and excludes failed-but-billed remote calls. New
append-only ledger:

```sql
CREATE TABLE ranking_remote_attempts (
    id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    call_id     bigint NOT NULL REFERENCES calls(id)    ON DELETE CASCADE,
    profile_id  bigint NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
    model       text   NOT NULL,
    outcome     text   NOT NULL CHECK (outcome IN
                    ('success', 'llm_error', 'parse_error')),
    created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ix_ranking_remote_attempts_created_at
    ON ranking_remote_attempts (created_at);
```

`RankResult` gains `escalation_attempted: bool` and
`escalation_outcome: str | None`; the worker inserts one ledger row per
attempted escalation (any outcome) in the same transaction as the
`CallRanking` merge. New setting `RANKING_REMOTE_DAILY_CAP` (default 100
attempts/day, Europe/Stockholm day — matching the proposal-assist cap
convention). The worker checks before each job:

```sql
SELECT count(*) FROM ranking_remote_attempts
WHERE created_at >= <stockholm_day_start>;
```

and passes `remote_client=None` once exhausted — `rank_pair` stays pure.
Single-instance constraint makes this race-free; a worker crash between the
remote call and the ledger write can lose one count (guardrail, not exact
ledger — same posture as the global token caps). Steady state is an
estimated 10–30 escalations/week; the cap exists for backfill spikes.

**Stale-analysis attribution** (Codex R5). The worker preserves prior
`summary`/`applicant_notes` when the current run produced none (worker.py
~155–171) — without which a local re-rank would clobber good Sonnet prose
over a transient outage. Keep the preservation, fix the attribution: new
nullable column `call_rankings.analysis_model` records which model produced
the *currently displayed* analysis. Written whenever this run produced
summary/notes; preserved alongside them when they're preserved; the
call-detail template's analysis-section attribution reads `analysis_model`
("Analysis by Sonnet 4.6"), while the score attribution keeps reading
`model` ("Scored by Gemma 4 E4B"). The two legitimately diverge after a
failed or capped escalation on a previously-escalated pair.

**Schema.** `call_rankings` gains `escalated boolean NOT NULL DEFAULT
false`, `escalated_from_score smallint NULL`, and `analysis_model text
NULL` (backfilled to `model` where `summary IS NOT NULL`); plus the
`ranking_remote_attempts` table above.

**Config.** Add `RANKING_ESCALATION_MIN_SCORE` (int, default 45) and
`RANKING_REMOTE_DAILY_CAP` (int, default 100). **Remove**
`REMOTE_RANK_COSINE_THRESHOLD` (and its `.env.example` line). Keep
`REMOTE_RANK_MODEL` and the `ANTHROPIC_API_KEY` on/off switch.

**UI.** The call-detail page already shows `model`; the admin debug section
additionally shows "escalated from N" when `escalated_from_score` is set.
No other UI change.

**Cost note.** Every surfaced call now costs one Gemma run + one Sonnet run.
In exchange: remote spend tracks user-visible value directly, is immune to
embedding-model drift, every digest-worthy call gets summary + applicant
notes (today only cosine ≥ 0.50 pairs do), and eligibility-unclear holds on
good calls get a second opinion from the model that can actually read
legalese.

### 3.4 Golden set → DB + admin curation

**Schema.**

```sql
CREATE TABLE golden_set_triples (
    id             bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    call_id        bigint NOT NULL REFERENCES calls(id)    ON DELETE CASCADE,
    profile_id     bigint NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
    expected_score smallint NOT NULL CHECK (expected_score BETWEEN 0 AND 100),
    note           text NULL,
    created_by     bigint NULL REFERENCES users(id) ON DELETE SET NULL,
    created_at     timestamptz NOT NULL DEFAULT now(),
    updated_at     timestamptz NOT NULL DEFAULT now(),
    UNIQUE (call_id, profile_id)
);
```

**Eval changes** (`ranking/eval.py`): `run_golden_set_eval(session_factory,
fixture_path=None)` — when `fixture_path` is given (unit tests), read the
JSON file exactly as today; otherwise read triples from `golden_set_triples`.
The DB unique constraint replaces the file-mode dedup warning. Tau math and
the admin tau panel are untouched.

**Durable eval history** (Codex R2). The latest-only sidecar
(`golden_set_last.json`, overwrite-in-place) cannot hold the before/after
comparison the rollout depends on. `_persist_report` additionally appends
one line — `{timestamp, n_fixture, n_compared, tau, prompt_version_counts}`
— to `$CALL_MANAGER_DATA_DIR/golden_set_history.jsonl`.
`prompt_version_counts` (a `{version: row_count}` map over the compared
rankings) is what makes a P3/P4 before/after readable: tau@v4.1-dominant vs
tau@v5.0-dominant on the same triples. The sidecar and admin panel keep
showing only the latest run.

**Admin curation panel** (new section on `/admin`, routes under
`/admin/golden-set`, POST + CSRF per house pattern):

- List current triples (call title, profile name, expected score, note,
  creator) with per-row delete.
- Manual add: call id + profile id + expected score + optional note.
- **Candidates list** — three mining queries, each `LIMIT 20`, each excluding
  pairs already in `golden_set_triples`, each rendered with an
  expected-score input and one-click add:
  1. *Dismissed despite high score:* `aggregate_score >= 60` AND a
     `user_call_dismissals` row exists from a user subscribed
     (`subscriptions`) to that ranking's profile.
  2. *Cosine/score disagreement:* `embed_similarity >= 0.5 AND
     aggregate_score <= 20`, or `embed_similarity < 0.3 AND
     aggregate_score >= 60`.
  3. *Escalation disagreement:* `escalated AND
     abs(escalated_from_score - aggregate_score) >= 40`.

Seeding target: 30–50 curated triples before the P3 (EV) version flip, so
tau-before vs tau-after is measurable on the same set.

### 3.5 Org-profile embedding text + re-embed

`embeddings/similarity.py::build_profile_text()` appends two segments after
`areas`:

```
<description>

<areas, one per line>

<org.capabilities, one per line>      # only when non-empty
<org.patient_populations, one per line>
```

No `kind` branching needed — the `org` namespace only exists on
`organizational_unit` profiles. `must_include` / `hard_exclusions` / numeric
fields stay excluded for the reasons documented in the function.

**Migration (data):** NULL `embedding` + `embedding_model` on **all** profile
rows (the migration-0010 pattern). The daily refresh tick repopulates ~15
profiles within a day; profile-edit saves re-embed immediately. Call vectors
are untouched.

**Re-embed trigger fix** (Codex R6). The profile-edit handler currently
re-embeds only when the *description* changed
(`refresh_embedding=description_changed`, profiles.py ~395) — already wrong
today for `areas` (in the embed text since Codex #2), and wrong for the new
org fields after this change. The handler instead compares
`build_profile_text()` over the pre-edit and post-edit profile state and
re-embeds when the text differs. This closes the pre-existing areas gap as
a side effect.

**Coverage/refresh blank-filters follow** (Codex R6). The admin embedding
coverage query and the daily refresh-missing tick both gate on non-blank
*description* — after this change a blank-description profile with areas or
org fields **is** embeddable and must be counted/refreshed. Both predicates
change to "would `build_profile_text()` be non-empty": description
non-blank, OR `structured->'areas'` non-empty, OR `structured->'org'->
'capabilities'` / `'patient_populations'` non-empty (SQL over the JSONB,
mirroring the Python). The two sites must stay in lockstep with
`build_profile_text` — note this in both docstrings.

### 3.6 Embedding-model calibration guard

New module-level registry (in `embeddings/` beside the client):

```python
THRESHOLD_CALIBRATIONS: dict[str, dict[str, float]] = {
    "bge-m3": {"pregate": 0.30, "hard_fail": 0.20},
}
```

At app startup (lifespan, after settings load): if
`settings.embedding_model` has no registry entry and **either** threshold
still equals its bge-m3-calibrated default (Codex R8 — requiring *both* at
default would let one overridden threshold silently suppress the warning
for the other), log a WARNING (`embedding.threshold_calibration_mismatch`)
naming the model and the specific still-default env var(s), and set a flag
the admin panel renders as a banner. Never refuses to start. A threshold
the operator has explicitly overridden is individually exempt — the
warning covers exactly the values still resting on another model's
calibration.

## 4. Rollout

Five independently shippable phases, lowest-risk first. Each lands with its
tests green; no phase depends on a later one.

| Phase | Contents | Migration |
|---|---|---|
| **P1** | Cosine tie-break (§3.2) + calibration guard (§3.6) | none |
| **P2** | `golden_set_triples` + eval DB mode + admin curation (§3.4); seed 30–50 triples | 1 (table) |
| **P3** | Logprob EV + `topic_fit_expected` + raw_response stripping + `validate_ev` command + eval history JSONL + `PROMPT_VERSION` v5.0 (§3.1), gated on the validation checkpoint | 1 (column) |
| **P4** | Outcome escalation, router removal, attempt ledger + cap, `analysis_model`, cosine-preservation removal, config add/remove (§3.3) | 1 (columns + ledger table) |
| **P5** | Org-profile embed text + re-embed (§3.5) | 1 (data) |

P2 before P3/P4 is deliberate: the golden set must exist before the scoring
regime changes, so tau-before/tau-after is measurable. Mining signal #3
(escalation disagreement) only populates after P4 — the panel ships with the
other two signals and picks it up automatically.

## 5. Testing

House style — pytest, duck-typed fakes, no live LLM in unit tests:

- **EV extraction:** fixture logprob envelopes — happy path; missing
  logprobs block; rationale prose containing "4/5" before the rating
  (offset binding must not bind to it); rationale emitted *before* rating
  inside topic_fit (key order not guaranteed); a rationale string
  containing the literal text `"rating": 4` (string-aware scanner must
  skip it); covering token that is multi-char (sanity check → None);
  degenerate single-digit top_logprobs. Property: EV is always within
  [0, 5] and None never raises.
- **Aggregation:** EV-vs-argmax precedence; cap/exclusion shapes on floats;
  rounding at bucket boundaries (EV 2.25 → 45, EV 2.95 → 59, EV 3.0 → 60).
- **Escalation matrix:** {score ≥ threshold / eligibility-fail + topic ≥ 3 /
  neither} × {remote present/absent} × {remote success/LLMError/ParseError}
  × {gate-fail short-circuit} — asserts on final score, `escalated`,
  `escalated_from_score`, `escalation_attempted`/`escalation_outcome`,
  `model`, analysis fields, and that local ParseError still raises.
- **Attempt ledger + cap:** worker writes one ledger row per attempt
  including failed outcomes; repeated rerank of the same pair produces
  multiple rows; cap shutoff passes `remote_client=None` from the ledger
  count; Stockholm day boundary.
- **Worker persistence changes:** current-run cosine written verbatim (NULL
  no longer preserved from the prior row); analysis preserved together with
  `analysis_model`; `analysis_model` set on fresh analysis.
- **validate_ev:** runs against seeded pairs, writes a timestamped report,
  and provably performs zero `call_rankings`/`call_ranking_criteria` writes.
- **Tie-break:** ordering with equal scores and NULL cosines (NULLS LAST) in
  digest assembly, dashboard list, and best-profile lookup.
- **Golden set:** CRUD routes (auth + CSRF), mining queries against seeded
  fixtures, eval DB-mode vs fixture-mode equivalence on identical triples,
  history JSONL appends one line per run with prompt_version_counts.
- **Migrations:** round-trip (upgrade/downgrade) per the
  `test_alembic_v2_round_trip.py` pattern; P5 data migration NULLs profile
  vectors only; P4 backfills `analysis_model` from `model` where summary
  exists.
- **build_profile_text:** org fields included for org profiles, absent for
  individuals; unchanged exclusions. Edit handler re-embeds on areas/org
  field changes (build_profile_text comparison), not just description;
  coverage + refresh-tick predicates count blank-description profiles with
  non-empty structured embed fields.

**Acceptance signals:** golden-set tau before/after P3 and P4 on the same
triples (expect non-degradation at minimum; the EV checkpoint in §3.1 gates
the flip); escalation volume vs cap in logs; borderline bucket containing
scores other than 50 after P3.

## 6. Out of scope / follow-ups

- **Setwise borderline comparison** (v2 spec phase 2) — superseded in
  priority by EV scoring; revisit only if tau says ordering is still weak.
- **BGE-reranker hybrid** (memory: v2 ranker) — deferral conditions
  unchanged; none have fired.
- **Self-consistency sampling** — `call_rankings.sample_count` already
  exists; if the EV validation checkpoint fails on real data, 3-sample
  median at temp > 0 is the fallback, at 3× local GPU cost on the
  post-gate residue.
- **FX conversion for the budget gate** — still deferred per the v2 spec.
- **Per-criterion golden-set bands** — aggregate-score triples first; add
  per-criterion expectations once the set has volume.
- **Score backfill to v5.0** — old rows stay v4.1; admin rerank on demand.
