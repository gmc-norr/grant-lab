**Match edition: usability and simplification review — 2026-10-31**

Reviewed source: `0fa6939e`. This extends the beta-readiness and security reviews with a researcher-facing walkthrough and an assessment of where complexity can actually be removed. Application code was left unchanged.

The match product has a coherent core: describe your research, review relevant funding calls, save a shortlist, and follow the funder's application instructions. Its single-column layout, visible Save/Hide controls, recoverable Hidden view, deadlines, and links to original sources support that job. The largest simplification opportunity is to give this product a firmer boundary from the future proposal workspace. Several smaller changes can improve the beta without a structural rewrite.

**What the size measurements mean**

Counts cover production Python under `src/grant_lab` and TypeScript under `frontend/src`, excluding frontend tests, generated declarations, dependencies, and built assets. They are physical source lines, including comments and blanks, rather than measures of behavioral complexity.

| Surface | Measured size | Interpretation |
|---|---:|---|
| Production Python | 311 files; 71,175 lines | The entire application, including future proposal work |
| `proposal_assist/` Python | 180 files; 38,414 lines | 54.0% of production Python is in the proposal subsystem alone |
| Remaining Python | 131 files; 32,761 lines | Includes shared infrastructure and further full-edition integration; this is not a clean match-only count |
| Handwritten frontend | 180 files; 19,636 lines | Both editions combined |
| Frontend modules present in the match build | 67 files; 8,069 source lines | Most handwritten frontend modules are already outside this bundle; individual files can also contain tree-shaken branches |
| Generated API types | 18,673 lines in `schema.gen.ts` | Generated contracts; their line count is not equivalent to handwritten maintenance work |
| Match main JavaScript chunk | 775.50 kB; 239.51 kB gzip | Initial download can be improved independently of source-code simplification |

About 31% of production Python consists of docstrings and full-line comments. Some carry necessary security and concurrency contracts; some recount review history or superseded implementations. Shortening those narratives would help reading, but would not remove application behavior.

Moving proposal code into an optional package would reduce the beta's dependencies and the scope developers must understand for a match release. It would not, by itself, reduce the total code the project owns. Actual deletion requires eliminating duplication, obsolete interfaces, or product requirements.

**Usability changes, in priority order**

1. **Make reversal visible and make notes deliberate.** In the real match UI, saving removes the card and opens “Why did you save …?” with a text field. There is no visible Undo button in the feed. The default Saved “Shortlist” has no Return to inbox button; selecting “Details” exposes it only on the focused card. A researcher should be able to correct a click without learning the keyboard controls or discovering the expansion model. Show a small “Saved — Undo” or “Hidden — Undo” confirmation, and expose Remove/Return on each saved or hidden item. Offer Add note on demand. This also creates an opportunity to simplify the automatic note-prompt and focus-management state. Retain the recent safeguards that bind writes to the correct profile, call, and decision; changing presentation alone does not make overlapping writes safe. Relevant files: `TriageFeed.tsx`, `TriageCard.tsx`, `DecisionNoteStrip.tsx`.

2. **Explain preparation before showing a finished matches screen.** Creating a profile leads to an edit screen with “Drafting your profile from PubMed and past grants”; Save is disabled while bootstrap runs. In a deliberately queued bootstrap fixture, visiting the feed for that profile showed all four open calls as its inbox, before profile ranking jobs existed. The feed's “Scoring N calls” state covers ranking jobs, rather than the preceding bootstrap. Keep a clear preparation message across both surfaces: “Preparing your research profile”, then “Finding your matches”, then the finished feed. Offer a clear route back to profile editing. The fixture demonstrates the state transition gap, not the time a functioning model will take. Relevant files: `ProfileNew.tsx`, `ProfileEdit.tsx`, `TriageFeed.tsx`, and the profile/bootstrap APIs.

3. **Expose the essential eligibility facts during setup.** The create form shows two research text boxes but collapses eligibility with the advanced options. Later, a warning explains that missing eligibility can cap scores and keep calls off top-match displays. Ask plainly whether the profile is for “Me” or “A research group”, what the research is about, and the country, institution/organization type, and application role needed for matching. Keep budgets, technology readiness, publication imports, and specialist preferences optional. Use “Research areas” as optional keywords with examples, or derive an editable suggestion from the description. This should be a short form, rather than another multi-step wizard. Relevant files: `ProfileNew.tsx`, `StructuredFields.tsx`, `ProfileOptions.tsx`, `EligibilityWarning.tsx`.

4. **Reduce the effort required to understand weak matches.** A seeded call scored zero still appeared under “Your matches” with Save and Hide. Source inspection confirms that the match UI supplies no minimum-score filter. At scale, researchers may have to dismiss large numbers of clearly irrelevant calls to achieve the promised finite inbox. Test a clearly labeled lower-fit group or an explicit “Show all calls” path, while keeping unranked calls distinguishable from calls judged irrelevant. Do not silently equate a missing score with a poor match. Preserve the requested numeric score, explain briefly what it means, and keep uncertain eligibility visible. Any score-filter change must keep list counts consistent; the existing decision-count query deliberately does not apply a score floor. Relevant files: `TriageToolbar.tsx`, `TriageFeed.tsx`, `dashboard.py`.

5. **Show ownership and keep profile context predictable.** The profiles list renders `organizational_unit`, explains that an “LLM ranks … the description and rubric”, and offers Edit for profiles the viewer cannot edit. The resulting page is a disabled form without a clear read-only explanation. Show human labels and “Yours”/“Shared with you”, and offer Edit only when permitted. The list API currently needs a permission field to support this cleanly. Separately, selecting a different profile and then clicking the top Calls navigation restores the account's default profile; this was reproduced in Chromium. Add an explicit default-profile choice or remember an intentional selection. Preserve the existing rule that merely opening a GET link does not change account preferences. Relevant files: `ProfilesList.tsx`, `ProfileEdit.tsx`, `SimpleShell.tsx`, `web/api/profiles.py`, `web/api/me.py`.

6. **Give occasional tasks less prominence.** On a 390-pixel-wide viewport, the header, view navigation, profile selector, search, funder filter, and order control occupy roughly the first 400 pixels. There was no horizontal overflow. A compact Filters disclosure would bring opportunities higher on the screen. Corridor boards are useful to coordinators but have the same navigation weight as matching for every researcher; consider a secondary tools entry, with ownership and publication permissions explained. Registration/pending-access screens should say how approval and initial access arrive, and offer the beta contact. Settings should advertise emailed digests only when delivery is available: the disposable instance displayed the Monday-email promise with no email transport configured. Relevant files: `SimpleShell.tsx`, `TriageToolbar.tsx`, `Register.tsx`, `AccountPending.tsx`, `Settings.tsx`, `BoardDetail.tsx`.

These are expert-review findings from source and a browser walkthrough. They establish confusing states and extra steps, but do not substitute for observing beta researchers. A useful first session is to ask a researcher to create a profile, explain a match, save three calls, reverse one decision, and find the official application instructions without coaching. Observe completion and hesitation before adding features.

**Where the implementation can become leaner**

| Order | Change | Concrete benefit and boundary |
|---|---|---|
| 1 | Remove the obsolete `needs_body` interface | Both Vinnova and EU adapters ignore it. Remove the protocol argument, compatibility introspection, callback, and source-wide body-ID query in `ingestion/orchestrator.py`. This deletes unused behavior and a database read, with a small review surface. Update adapter tests rather than retaining compatibility for obsolete test doubles. |
| 2 | Share the email delivery implementation | `auth/email.py` and `email/client.py` both implement SMTP and Resend. Keep one delivery implementation and adapt plain-text auth notifications to it. Preserve TLS, recipient-bounce classification, safe logging, and delivery-failure semantics. The two callers have different policies, so their higher-level behavior should remain explicit. |
| 3 | Finish the match/workspace runtime boundary | `scheduler.py` still registers workspace jobs, and several ticks import their workspace implementation before checking `drafting_enabled`; `_coherence_tick` at line 1143 is one example. Auth/admin revocation paths also reach collaboration code. Have the full edition explicitly register its workspace jobs and revocation integration. Keep required cleanup/reapers active in the full edition when drafting is paused; an edition boundary and a kill switch serve different purposes. This is a better next boundary than adding more scattered flag checks. |
| 4 | Make workspace dependencies optional once that boundary works | `claude-agent-sdk`, `pycrdt`, ProseMirror, and the workspace document-upload parsers are candidates. Verify by installing and exercising match without them. Keep `anthropic` if hosted ranking remains enabled; it is not exclusively a drafting dependency. Keep PyMuPDF while the shared source-extraction code imports it. Preserve shared database models and migration history during the initial split. |
| 5 | Consolidate repeated workspace operations within the future product | The four pass runners total 1,797 lines. They repeat bounded model exchange, timeout, usage capture, termination, and cancellation handling. Share that lifecycle while keeping domain-specific transactions and finalization explicit. The three workspace-gone handlers in `main.py` also have identical response bodies and can share a handler without merging their domain exceptions. These cuts help future workspace development and do not need to delay match beta. |
| 6 | Simplify exceptional access queries and historical prose | `_readable_ignoring_ownership` uses a synthetic user with ID `-1`, then separately restores the real viewer-grant check. An explicit owner-arm option in the shared predicate would express the request directly. Preserve one source of access rules and its regression tests. Move lengthy review chronology into existing design/research notes, leaving concise current invariants beside the code. |

For the larger boundary, start inside the existing repository: one match composition path and one explicit workspace registration point for routes, jobs, and lifecycle integration. Then prove match works without workspace dependencies before changing packaging. This avoids a new service, another deployment, or a new permission model. Separate packaging is worthwhile only if it makes match installation and releases materially simpler.

The future workspace also has a product-level complexity lever already examined in the August fence-elimination investigations: restore into a new workspace identity/path rather than reusing the deleted identity. That can remove mechanisms whose purpose is keeping stale writers out of a restored identity. It changes restoration and URL semantics, needs migration and concurrency validation, and is a separate future-product decision. It is not permission to remove current locking, retirement, or generation checks as cleanup. See `docs/superpowers/reviews/2026-08-25-grok-fence-elimination-architecture-review.md` and its independent companion review.

**Recommended sequence and acceptance**

For beta, keep the current React match UI, FastAPI, PostgreSQL, ingestion/ranking pipeline, and single-instance deployment model. Replacing React with server rendering would be a substantial UI rewrite: the simpler match edition is itself React, and `SPA_MODE=disabled` supplies no replacement UI. No evidence in this review makes that rewrite the best near-term simplification.

First fix the concrete usability gaps around setup, preparation, and reversing decisions. Remove `needs_body` and consolidate email in separate small changes. Their acceptance checks are stable ingestion behavior without the body scan, unchanged source closure/freshness handling, and unchanged email TLS/bounce/error behavior. Exercise the user journey in both desktop and mobile layouts after the UI changes.

Next isolate workspace registration and dependencies. Acceptance should cover a real match lifespan, scheduled job invocations, login/logout/password reset and admin revocation, plus profile/triage/board operations with the workspace extras absent. A `create_app()` import-only check is insufficient. Retain full-edition tests to prove that paused-drafting cleanup and access revocation still work. Keep the generated architecture map and edition-bundle checks current if code moves.

After beta observations, decide which optional product workflows earn their maintenance cost. For example, manual research-description entry with publication enrichment available later could simplify automatic profile bootstrap, but this changes the product contract and should be judged against researcher effort and match quality. A code reduction target alone cannot decide it.

**Validation and limits**

Built the current match frontend successfully into a temporary directory. Reviewed the emitted module manifest and measured source sizes. Walked the built frontend against the real API and migrated disposable PostgreSQL database using a non-admin researcher, an owned profile, a shared read-only profile, saved decisions, and synthetic calls. Inspected desktop screenshots at 1440 pixels and mobile screenshots at 390 pixels. Verified no horizontal overflow in the mobile inbox and no page errors in the main walkthrough. Reproduced Saved-control visibility, the read-only edit form, queued-bootstrap behavior, and default-profile restoration through navigation.

The server deliberately disabled lifespan workers, so the walkthrough made no model, ingestion, email, or identity-provider requests. Bootstrap was intentionally left queued to inspect that UI state. This review did not measure model quality or production latency, run new usability sessions with researchers, or repeat the earlier full regression/security suites. Only this review document was added to the repository.
